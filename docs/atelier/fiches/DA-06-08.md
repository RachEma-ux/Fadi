# DA-06-08 — Building-element classification / Classification des éléments du bâtiment — module M05 → module Fadi Atelier — lot 3a

**État : spécifiée** (à spécifier → spécifiée → prototype → vérifiée → disponible). Preuve liée : — (à lier au lot 3a ; classes IFC déclarées par l'ontologie au lot 1, L1.1).

| Champ | Contenu |
| --- | --- |
| Identité | **DA-06-08** « Building-element classification » (Exigences V4, annexe B.7, module M05, étape cible P1 ; critère commun B.7). Objet : la classification d'un objet du bâtiment, au sens du cahier §5.2 (« propriétés BIM et classification (classe IFC, code de classification optionnel) ») et de l'Architecture V4 §4 (« plusieurs classifications à un même objet sans confondre ses représentations » ; « classifications externes … conservées séparément »). Sous-exigences : **DA-06-08-a** classe d'ontologie et classe IFC 4.3 de chaque objet, lues dans l'inspecteur ; **-b** affecter, remplacer ou retirer un code d'un système de classification déclaré ; **-c** plusieurs classifications par objet (systèmes différents) ; **-d** classification portée par une définition (type) et héritée ; **-e** sélectionner / filtrer par classe d'ontologie et par code. Distinct de **DA-05-02** « Classes » (organisation d'affichage de type CAO, fiche A) et de la `categorie` d'une pièce (donnée de projet de P.118, DA-07-15). Fiches liées : DA-06-07, DA-05-12, DA-05-14 / 15, lot 6 (IFC). |
| Situation utilisateur | L'architecte veut savoir, pour chaque objet, « ce que c'est » pour les échanges et les tableaux (mur → `IfcWall`, solide générique → `IfcBuildingElementProxy`), et, si son bureau ou le maître d'ouvrage utilise un système de classification, rattacher un code à un objet ou à un type pour trier tableaux et quantités, sans changer la nature de l'objet. |
| Entrées et unités | `objetIds` ou `definitionId` ; `systeme` (identifiant d'un système de classification **déclaré dans le projet** : nom, édition, source — aucun système n'est déclaré par défaut, R3) ; `code` (texte, tel que publié par le système) ; `libelle` (facultatif, texte du système) ; `provenance` (`saisie` / `import`). Pas d'unité (données qualitatives). La classe d'ontologie (`mur`, `porte`…) et la classe IFC correspondante sont **dérivées** de l'ontologie (`packages/atelier-model/src/ontologie/**`), non saisies : `niveau` → `IfcBuildingStorey`, `mur` → `IfcWall`, `porte` → `IfcDoor`, `fenetre` → `IfcWindow`, `ouverture` → `IfcOpeningElement`, `dalle` → `IfcSlab` (`FLOOR`), `toiture` → `IfcRoof` / `IfcSlab` (`ROOF`), `escalier` → `IfcStair`, `piece` / `espace` → `IfcSpace`, `zone` → `IfcZone`, `poteau` → `IfcColumn`, `solide` → `IfcBuildingElementProxy` (annexe C). |
| Comportement | Sélection → inspecteur, bloc « Classification » : classe d'ontologie et classe IFC (lecture seule, avec l'ontologie d'origine `building.architecture`, `building.structure`, `drawing`, `annotation`), puis la liste des codes par système → ajout d'un code : choix du système déclaré, saisie du code → contrôle (système déclaré, code non vide, pas de doublon du même système sur l'objet, droits `write`) → aperçu (tableaux qui trient par ce système marqués « à recalculer ») → validation = commande `classification.affecter` (annexe B, famille Organisation ; retrait figé par L1.2 dans la même famille). Sélection multiple : une commande atomique. Sur une définition : le code est hérité par les occurrences ; un code d'occurrence prime et est signalé « surchargé ». **Changer la classe d'ontologie** d'un objet (ex. mur → garde-corps, solide → mur) n'est **pas** une classification : c'est une conversion métier explicite, hors lot 3 (DA-07-20 hors périmètre ; garde-corps DA-07-12 au lot 5) ; elle est refusée par `classification.affecter`. Filtre de sélection par classe et par code (L3a.2). |
| Données et dépendances | `atelier_properties` ou table de classification dédiée (choix de stockage délégué au chef de projet, §10.2, à consigner) avec `{ objet ou definition, systeme, code, libelle, provenance }` ; catalogue des systèmes déclarés au niveau du projet (`atelier_site` ou table du projet, à figer par L2.1) ; ontologie (classe IFC par classe) dans `atelier-model`. Événement `atelier.commande.validee` → tableaux et exports marqués périmés. Le `role` des solides de P.118 reste une donnée du `solide` (cahier §6 : « role conservé tel quel ») et n'est pas une classification. |
| Résultats | Classe IFC visible pour chaque objet ; codes de classification par système ; filtres de sélection ; critère de tri et de regroupement des tableaux (lot 5) ; `IfcClassificationReference` à l'export (lot 6) ; journal et révision `n + 1`. |
| Cas limites | Système non déclaré → refus 400 « système de classification inconnu : le déclarer d'abord ». Code vide → refus. Deux codes du même système sur un objet → refus (ou remplacement explicite). Tentative de changer la classe IFC d'un mur par code → refus « la classe découle de l'ontologie ». Objet importé avec une classe inconnue (rôle de solide inconnu) → reste `solide` / `IfcBuildingElementProxy`, listé dans le rapport d'import, jamais reclassé silencieusement (annexe C). Objet supprimé entre-temps → 409. Requête répétée → une seule révision (T06). Rôle `read` → 403. |
| Compatibilité | **Import P.118** : la source ne contient **aucune** classification externe → aucun code créé ; classes d'ontologie dérivées de la famille source (walls → `mur`, doors → `porte`, etc., cahier §6) ; les 870 tracés à rôle `solid`, `clearance`, `ramp-*` deviennent `solide` avec `role` conservé (classe IFC `IfcBuildingElementProxy`) ; la catégorie des pièces (`Services` 18, `Circulation` 12, `Administration` 9, `Activités` 5, `Accueil` 1) reste un paramètre `categorie` de la pièce. **IFC 4.3** (lot 6) : classe d'entité selon l'annexe C ; codes en `IfcClassification` + `IfcClassificationReference` + `IfcRelAssociatesClassification` — correspondance **non évaluée**, à fixer au lot 6 avec le corpus. Aucun système (Uniclass, OmniClass, CFC / eCCC, etc.) n'est présumé. |
| Validation | **Unité `packages/atelier-model`** : chaque classe de l'ontologie a sa classe IFC (table complète, test exhaustif sur l'annexe C) ; `classification.affecter` sur un objet et sur une définition, héritage et surcharge, inverse exact ; refus d'un système non déclaré, d'un doublon, d'un changement de classe d'ontologie ; import P.118 : zéro code de classification créé, 870 solides en `IfcBuildingElementProxy` avec `role` conservé. **API** : 400 détaillé, 403 rôle `read`, idempotence. **Scénario `05-atelier.mjs`** : sur P.118, lire « IfcDoor » sur une porte ; si un système de test est déclaré par le scénario (données de test, pas une valeur de projet), affecter un code à deux portes, filtrer la sélection par ce code, annuler. |
| Règles métier | Une classification ne vaut ni exigence ni conformité : elle classe, elle ne contrôle pas. Aucune règle réglementaire n'est déclenchée par un code (R3). Les codes et libellés d'un système sont repris tels que publiés, avec la source et l'édition du système (R4 : la source est tracée). |
| Extensions à spécifier | Import de codes depuis IFC (lot 6) ; classifications portées par les tableaux et quantités (lot 5) ; conversion de classe d'ontologie par commande explicite (garde-corps, DA-07-12, lot 5). **Question au maître d'ouvrage** : quel système de classification (et quelle édition) votre pratique utilise-t-elle, s'il en faut un dès le lot 3 ? À défaut, seule la classe d'ontologie / IFC est livrée et l'affectation de codes reste disponible pour des systèmes déclarés par l'utilisateur. |
