| Champ | Contenu |
| --- | --- |
| Identité | DA-21-01 (M16, étape cible P1). Plusieurs personnes travaillent sur le même modèle de l'Atelier avec des droits distincts et une réservation d'édition. Sous-exigences : -a droits par rôle (`read`, `comment`, `write`, `owner`) relus par le serveur à chaque requête ; -b réservation d'édition existante de Collaboration respectée par le service de commandes (423) ; -c réservation par niveau ou par objet, réservation de variante : extension (lot 7). Référence de comportement : réservation existante de Fadi (R13) ; aucun comportement du prototype. |
| Situation utilisateur | Travailler à plusieurs sur une même maquette sans écraser le travail d'autrui : savoir qui peut écrire, qui détient la réservation, et ce qui est refusé et pourquoi. |
| Entrées et unités | `projectId` ; rôle de la personne sur le projet (`read`, `comment`, `write`, `owner`) ; état de la réservation d'édition (titulaire, échéance éventuelle : tels que fournis par la réservation existante de Collaboration, que le lot 2 relève sans la modifier) ; enveloppe de commande (section 5.3 : `requestId`, `baseRevision`). Aucune unité propre. |
| Comportement | **Droits.** Relus par le serveur à chaque requête (R13) : lecture (`GET /model`, `/model/niveaux/:niveauId`, `/journal`, `/problemes`) dès `read` ; commande (`POST /commands`, `/commands/annuler`, `/commands/retablir`) exige `write` ; 404 sans accès au projet ; 403 motivé (rôle insuffisant, rôle exigé nommé) ; jamais contourné par le client : masquer un outil est une aide, pas un contrôle. |
| | **Réservation.** Tant qu'une autre personne détient la réservation d'édition, `POST /commands`, `/commands/annuler` et `/commands/retablir` répondent 423 motivé et ne changent ni la révision ni le journal ; le lot est refusé en entier. Lecture et exécution à blanc (`/commands/essai`) ne sont pas concernées (rien n'est écrit). Prendre ou libérer une réservation n'est pas une commande du modèle : aucune révision (R10). |
| | **Réservation et révision.** La réservation ne remplace pas le contrôle de `baseRevision` : son titulaire reçoit 409 si sa `baseRevision` est périmée (par exemple depuis un second navigateur, DA-21-02). Au lot 2, la portée et la durée de la réservation sont celles de Collaboration, relevées et consignées sans être inventées ; réservation par niveau ou par objet : extension. |
| | **Interface (R20).** États vide, chargement et erreur explicites : bannière « lecture seule : réservation détenue par … » ; messages distincts pour 403 (rôle exigé nommé), 404 (projet introuvable ou sans accès) et 423 ; outils d'édition désactivés avec la raison disponible au survol et au lecteur d'écran ; brouillon en cours conservé. |
| Données et dépendances | Aucune classe du modèle modifiée ; `projects.model_revision`, journal et boîte de sortie inchangés par un refus 403, 404 ou 423 ; rôles et réservation lus depuis Collaboration (source unique, aucune copie dans le modèle typé) ; événement `atelier.commande.validee` seulement pour un lot validé. |
| Résultats | Réponse 403 motivé, 404 ou 423 motivé ; bannière de lecture seule avec le titulaire ; brouillon conservé ; aucune écriture partielle (lot atomique). |
| Cas limites | **Réservation et droits.** Réservation prise par autrui entre l'aperçu et la validation → 423, lot conservé en brouillon ; réservation expirée ou libérée pendant la file hors ligne : rejeu normal, contrôlé par `baseRevision` ; titulaire déconnecté : règle de Collaboration, non modifiée ; rôle abaissé en cours de session : relu à chaque requête, 403 au rejeu, brouillon conservé ; accès retiré : 404. |
| | **Requête répétée et réseau.** Même `requestId` rejoué après un refus : le refus n'est pas une validation, aucune réponse enregistrée (T06) ; hors ligne : file Dexie (une entrée par lot), rejeu dans l'ordre à la reconnexion ; un 423 ou un 403 au rejeu arrête le rejeu, les lots restants sont conservés en brouillon, sans perte ni réordonnancement. |
| Compatibilité | Contrat `atelier-commands/1` (versionné) ; API de la section 5.4 ; Express 5 et PostgreSQL (verrou sur la ligne du projet) ; réservation et rôles de Collaboration inchangés. |
| | Import P.118, IFC, DXF : sans objet (aucune donnée de collaboration dans ces formats). |
| Validation | **Unité** : sans objet pour la réservation (service existant) ; les réducteurs purs (`packages/atelier-model/src/commandes/*.test.ts`) ne dépendent ni des droits ni de la réservation. |
| | **API** (`apps/api/src/routes/atelier-commands.test.ts`, groupe « droits et réservation ») : rôle `read` → 403 motivé sur `POST /commands`, 200 sur `GET /model` ; sans accès → 404 ; réservation d'autrui → 423 sur `/commands`, `/commands/annuler` et `/commands/retablir`, révision et journal inchangés ; réservation de la personne → 200 ; titulaire avec `baseRevision` périmée → 409 ; `/commands/essai` → 200 malgré la réservation d'autrui. |

| Règles métier | Aucune règle réglementaire. R13 : droits relus par le serveur à chaque requête, 404 sans accès, 403 motivé, 423 pendant une réservation d'autrui ; les équipiers et les scripts ne contournent jamais un refus.
