# DA-21-07 — Revision tracking / Suivi des révisions — module M16 → Collaboration et Atelier — lot 2

**État : prototype (lots 2, 5, 7)** (à spécifier → spécifiée → prototype → vérifiée → disponible). Preuve liée : `apps/api/src/routes/atelier-commands.test.ts` (révision, empreinte, péremption ; production tardive rattachée à sa révision, lot 9), versions nommées (lot 7) ; comptes rendus `lots/lot-2.md`, `lot-5.md`, `lot-7.md`.

| Champ | Contenu |
| --- | --- |
| Identité | DA-21-07 (M16, étape cible P1). La révision est le numéro d'état du modèle ; chaque donnée dérivée (vue, feuille, tableau, export, bilan) porte la révision et l'empreinte dont elle est issue et sait si elle est actuelle ou périmée. Sous-exigences : -a numéro de révision et `baseRevision` ; -b empreinte et péremption des dérivés (R11, T07) ; -c bilan Harmonie et aperçu conceptuel périmés ; -d révisions nommées (extension, lot 7). Référence de comportement : aucune ; le prototype porte `architectureRevision`, `rampRevision` et `designRevision`, conservées comme propriétés de provenance `import`. |
| Situation utilisateur | Savoir à quelle révision correspond chaque document ou calcul, voir s'il est à jour, et ne jamais présenter comme actuel ce qui provient d'une révision plus ancienne. |
| Entrées et unités | `revision` du modèle (entier croissant, `projects.model_revision`) ; `baseRevision` de chaque lot ; `empreinte` d'un dérivé (empreinte des entrées dont il est issu) ; `revisionCourante` renvoyée par un 409 ; événement `atelier.commande.validee { revision, objetIds, types }`. Aucune unité propre. |
| Comportement | **Numérotation.** Une révision par lot validé (annuler et rétablir compris), numéros contigus, jamais réutilisés ni renumérotés ; le client nomme toujours la révision qu'il affiche (« révision n ») ; un 409 renvoie `baseRevision` et `revisionCourante` pour que l'écart soit explicite. |
| | **Dérivés.** Un dérivé enregistre la révision et l'empreinte de ses entrées et déclare ses dépendances (objets, classes, niveaux). À chaque événement, un dérivé dont les dépendances recoupent `objetIds` ou `types` passe « périmé » : il reste consultable avec un bandeau, jamais présenté comme actuel (R11). La péremption est aussi vérifiée à la lecture (révision d'origine antérieure et empreinte différente), sans dépendre de la seule livraison de l'événement. Recalcul à la demande, jamais en silence. |
| | **Bilan Harmonie et aperçu conceptuel.** Chaque lot validé périme le bilan Harmonie et invalide l'aperçu conceptuel (section 5.4) ; ils portent la révision dont ils sont issus et se recalculent à la demande. |
| | **Révisions du prototype et révisions nommées.** `architectureRevision`, `rampRevision`, `designRevision` de P.118 sont des propriétés de provenance `import` : jamais interprétées comme la révision du modèle, jamais incrémentées par une commande. Une révision nommée (jalon) désigne une révision et son empreinte : extension (lot 7). |
| Données et dépendances | `projects.model_revision` ; journal ; documents dérivés (révision, empreinte, état actuel ou périmé) ; bilan Harmonie ; aperçu conceptuel ; boîte de sortie ; propriétés de projet `architectureRevision`, `rampRevision`, `designRevision` (provenance `import`). |
| Résultats | Chaque dérivé affiche sa révision, son empreinte et son état ; `GET /problemes` liste les documents périmés et les réserves Harmonie ; un 409 explicite les deux révisions. |
| Cas limites | **Écart.** Dérivé généré à une révision postérieure à celle que le client affiche : le client se resynchronise (DA-21-02) avant de l'afficher comme actuel ; empreinte absente : dérivé traité comme périmé, jamais comme actuel ; événement perdu ou retardé : péremption constatée à la lecture. |
| | **Concurrence, réseau, droits.** `baseRevision` périmée → 409 avec `revisionCourante` ; même `requestId` → aucune seconde révision (T06) ; hors ligne : dérivés locaux marqués « révision locale, non synchronisée » ; 403 motivé, 404 sans accès, 423 pendant une réservation d'autrui (R13). |
| Compatibilité | Contrat `atelier-commands/1` ; empreinte : algorithme et sérialisation canonique versionnés (choix consigné dans `decisions.md`) ; import P.118 : deux imports donnent même modèle, même empreinte (section 6) ; tout export (IFC, DXF, lots 5 et 6) porte la révision et l'empreinte dont il est issu (R11). |
| Validation | **Unité** (`packages/atelier-model/src/…`) : empreinte du modèle identique pour deux sérialisations équivalentes (ordre des clés), différente après toute modification ; deux imports de P.118 : même empreinte. |
| | **API** (`apps/api/src/routes/atelier-commands.test.ts`, groupe « révisions ») : révisions contiguës après N lots ; 409 renvoie `baseRevision` et `revisionCourante` ; lot validé : document de test dépendant « périmé », document non concerné inchangé, bilan Harmonie « périmé » ; événement rejoué : un seul marquage ; dérivé sans empreinte : périmé ; `GET /problemes` liste les périmés. |
| | **e2e** (`apps/web/e2e/scenarios/05-atelier.mjs`, bloc « Collaboration · révisions ») : copie de travail de P.118 : bandeau « révision n » ; après modification d'un mur, le bilan Harmonie est « à recalculer », indique la révision dont il est issu et reste consultable ; recalcul à la demande : révision et empreinte mises à jour ; second navigateur à la même révision. |
| Règles métier | Aucune règle réglementaire. R11 : un dérivé porte la révision et l'empreinte dont il est issu ; périmé, il reste consultable mais n'est pas présenté comme actuel (T07). R3 : un dérivé sans révision ni empreinte n'est jamais présumé actuel. R9 : seul le service de commandes crée une révision. R10 : afficher une révision n'en crée pas. Critère B.22 : conflits et révisions explicites. |
| Extensions à spécifier | Révisions nommées et jalons (lot 7) ; comparaison de deux révisions (DA-21-08, P2) ; indice de révision propre à chaque feuille (lot 5) ; notifications de péremption. |
