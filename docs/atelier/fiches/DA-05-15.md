# DA-05-15 — Standard-component libraries / Bibliothèques de composants standard (types de portes, fenêtres, ouvertures) — module M04 → Atelier — lot 3a

**État : prototype (lot 3a)** (à spécifier → spécifiée → prototype → vérifiée → disponible). Preuve liée : recette `apps/web/e2e/atelier-nouveau.mjs`, tests `apps/web/src/modules/atelier/nouveau/nouveau.test.ts` et `packages/atelier-model/src/commandes/commandes.test.ts` ; compte rendu `lots/lot-3a.md`.

| Champ | Contenu |
| --- | --- |
| Identité | DA-05-15 (M04, étape cible P1). Interprétation retenue : les « composants standard » sont les types réutilisables des éléments hébergés par un mur (`porte`, `fenetre`, `ouverture`), dans le même catalogue versionné que DA-05-14 : mêmes commandes `type.definir` et `type.modifier`, mêmes règles de version et de propagation. Sous-exigences : -a définir un type de porte, de fenêtre ou d'ouverture ; -b le modifier (version n + 1) ; -c l'appliquer et consulter ses usages. Les composants placés et comptés (mobilier, équipements) relèvent de DA-05-09 (lot 5). |
| Situation utilisateur | Définir les types de portes, de fenêtres et d'ouvertures du projet et les appliquer aux ouvertures posées dans les murs, avec contrôle d'emprise. |
| Entrées et unités | `type.definir` : `classe` (`porte`, `fenetre`, `ouverture`), `typeId`, `nom`, `valeurs` facultatives (`largeur`, `hauteur`, `allege` : `{ value, unit: "m" }`), propriétés facultatives (DA-06-07). Application : `typeId` dans `ouverture.poser` ou `ouverture.modifier`, avec `murHoteId`, `position` (t ∈ [0,1] le long de l'axe) et `repere` facultatif. |
| Comportement | **Cycle.** Panneau Types (onglet ouvertures) → type ou « Nouveau type » → paramètres → aperçu (ouvertures qui emploient le type, écarts, emprise dans les murs hôtes) → contrôle → validation ; Échap annule sans commande. Poser une ouverture avec un type propose ses valeurs : l'utilisateur les confirme ou les change, la valeur de l'occurrence restant canonique (R15). |
| | **Propagation.** Comme DA-05-14 : `type.modifier` crée la version n + 1 sans toucher aux ouvertures posées ; « propager » ne modifie que les ouvertures cochées, après contrôle d'emprise, dans le même lot, effets listés. |
| | **Emprise (R12).** Une valeur propagée qui ferait sortir une ouverture de son mur hôte ou la ferait chevaucher une autre est refusée à l'aperçu pour cette ouverture, qui reste inchangée si le lot est validé sans elle ; aucune ouverture ne passe « à réparer » par un simple changement de type. Un type de porte ne s'applique pas à une fenêtre (refusé). |
| Données et dépendances | Entité `definition` (classes `porte`, `fenetre`, `ouverture`) ; `typeId` et version d'alignement portés par chaque ouverture (§5.2) ; relation `heberge-par` inchangée ; relation d'usage dérivée. Événement de commande validée : vues, quantités et bilan Harmonie « à recalculer » (R11, T07) ; microversion +1. |
| Résultats | Type d'ouverture créé ou versionné ; ouvertures alignées à la demande, listées ; catalogue consultable avec ses usages ; inverse restitue type et ouvertures. |
| Cas limites | **Valeurs.** `largeur` ou `hauteur` ≤ 0 ou unité ≠ m refusées (T03) ; `allege` absent : « non évaluée » (une fenêtre sans allège reste affichable, quantités sans valeur) ; type de porte sur une `fenetre` refusé ; ouverture importée sans type : conservée sans type, jamais rattachée par déduction (R3). |
| | **Concurrence et réseau.** `baseRevision` dépassée et type ou mur hôte modifié depuis → 409 avec `conflits[].objetId` ; ouverture supprimée par autrui pendant une propagation : 409, elle ne réapparaît pas ; même `requestId` → une seule version (T06). Hors ligne : réducteur local, file Dexie, rejeu dans l'ordre, brouillon si le type a changé. 403 / 404 / 423 selon R13. |
| Compatibilité | Import P.118 : 84 `porte` et 126 `fenetre` avec leur `typeId` et leur `repere` tels qu'exportés, sans type ajouté ni complété ; les 210 ouvertures restent hébergées par leurs murs. IFC : `IfcDoorType` et `IfcWindowType` avec `IfcRelDefinesByType` à l'export (annexe C, lot 6) ; ouvertures sans type : exportées sans `IfcRelDefinesByType`, nommées au rapport. DXF : sans objet. |
| Validation | **Unité** (`packages/atelier-model/src/commandes/type.test.ts`, cas ouvertures) : type de porte défini et appliqué à une porte ; modification sans `propager` : portes inchangées ; avec : seule la porte citée change ; propagation qui sort du mur hôte refusée pour cette porte ; type de porte sur une fenêtre refusé ; inverse restitue. |
| | **API** (`apps/api/src/routes/atelier-commands.test.ts`) : `type.definir` (porte) → 200 ; largeur négative → 400 avec `chemin` ; `ouverture.poser` avec un type inconnu → 400 ; même `requestId` → même réponse ; `baseRevision` périmée → 409. |
| | **e2e** (`apps/web/e2e/scenarios/05-atelier.mjs`, bloc « Organisation · types d'ouvertures ») : copie de travail de P.118 : porte `EX118-mezz-D-001` à t = 0,5 ; définir un type, l'appliquer à une nouvelle porte posée sur un mur de la mezzanine à un emplacement libre, modifier le type avec propagation sur la nouvelle porte seulement ; `EX118-mezz-D-001` inchangée ; annuler ; second navigateur à la même révision. |
| Règles métier | Aucune règle réglementaire : largeurs de passage, hauteurs et allèges minimales ne sont ni fournies ni contrôlées (R3) ; les valeurs d'un type sont des valeurs déclarées. R12 : emprise contrôlée, jamais de rattachement silencieux. |
| Extensions à spécifier | Ouvertures composées (porte-fenêtre) ; types à profils et quincaillerie (DA-05-17, DA-05-18 : P2) ; bibliothèques de fabricants ; retrait ou suppression d'un type ; gabarits d'ouverture (cadre, seuil, recouvrement). |
