| Champ | Contenu |
| --- | --- |
| Identité | **DA-21-05** « Integrated data management » (Exigences V4, annexe B.22, module M16, étape cible P1 ; critère commun B.22). Retenue aux lots 2 et 7. Objet : un **seul projet** porte le modèle typé, ses définitions et catalogues, ses hypothèses et sources, ses volumes immuables, ses documents dérivés et ses liaisons au programme, sous une autorité unique, avec des propriétaires de données identifiés et une sauvegarde cohérente (Architecture V4 §3 « Données », §9 ; Exigences V4 annexe A, SOLIDWORKS PDM : « séparer métadonnées et volumes »). Sous-exigences : **DA-21-05-a** (lot 2) tables du module Atelier (`atelier_*`, cahier §5.5), propriété du module, migration idempotente dans la section `atelier` d'`init.sql` ; **-b** (lot 2) volumes immuables (`volumes`, identifiant SHA-256) derrière l'interface `VolumeStore` ; **-c** (lot 2) écriture du modèle, du journal et de la boîte de sortie dans **une** transaction ; **-d** (lot 2, puis 4 et 9) sauvegarde et restauration vérifiées incluant journal, volumes, versions, publications (T11) ; **-e** (lot 4) archive du projet en modèle typé (version d'archive incrémentée), import des archives antérieures et des exports du prototype ; **-f** (lot 4) consommateurs (analyse, bilan Harmonie, documents, aperçu, transmission de la parcelle) lisant la **projection** du modèle typé, jamais ses tables (cahier §5.6, T14). Fiches liées : DA-21-04, DA-21-07, DA-05-11 (références externes, lot 7, fiche A). |
| Situation utilisateur | L'architecte retrouve dans un même projet le modèle, ses hypothèses (H01…), ses sources (CAD-S01…), ses documents produits et le programme lié ; il exporte le projet et le restaure ailleurs sans perte ; l'administrateur restaure une sauvegarde et retrouve un ensemble cohérent. |
| Entrées et unités | Projet ; contenus typés du modèle (unités SI, repères tagués, R5) ; volumes (`mime`, `size` en octets, contenu) ; archive JSON avec manifeste versionné (schémas, unités, repères, identités, versions de catalogues, cahier §5.10). Limites : enveloppe ≤ 1 Mo, volume ≤ 25 Mo (cahier §8). |
| Comportement | Toute mutation du modèle passe par le service de commandes (R9) ; aucune route hors de ce service n'écrit dans `atelier_*`. Un volume est écrit (et dédupliqué par son SHA-256) **avant** d'être référencé par une commande validée ; un volume non référencé est récupérable par une politique dédiée (Architecture V4 §6), jamais supprimé pendant qu'une transaction peut le référencer. Les autres modules lisent le modèle par la projection pure de `packages/atelier-model` (`modèle typé → entrée d'analyse`, cahier §5.6) ou par l'API, jamais par les tables (manifeste et `check-module-deps`, T14). Export : archive = modèle typé + journal + hypothèses + sources + références de volumes (contenus inclus si redistribuables) + manifeste ; import : par l'importeur du lot 1 (archives antérieures et exports du prototype), rapport nominatif (R7). Restauration : `scripts/backup.sh` / `restore.sh` / `verify-restore.sh` couvrent les nouvelles tables et volumes. |
| Données et dépendances | `atelier_definitions`, `atelier_objects`, `atelier_properties`, `atelier_relations`, `atelier_representations`, `atelier_layers`, `atelier_site`, `atelier_commands`, `atelier_outbox`, `volumes` (cahier §5.5) ; `produced_documents`, `drawing_exports` (existants) ; Programmation (`roomLinks`, existant) ; archive (`project-archive.ts`, `packages/domain-model/src/archive.ts`, lot 4) ; `VolumeStore` (`apps/api/src/lib/volume-store.ts`, implémentation base aujourd'hui, stockage objet plus tard hors dépôt, §10.1 point 4). |
| Résultats | Données du projet cohérentes et restaurables ; archive exportable et réimportable ; rapport d'import ; aucun accès direct d'un module aux tables d'un autre. |
| Cas limites | Échec en cours de transaction → rien n'est écrit (ni modèle, ni journal, ni événement). Volume dépassant 25 Mo → 413 motivé. Volume de même SHA-256 déjà présent → réutilisé. Archive d'une version de manifeste inconnue → refus motivé, rien d'importé. Archive du prototype incomplète → import de ce qui existe, manques listés au rapport, rien d'inventé (R3, R7). Restauration d'une base sans volumes référencés → `verify-restore.sh` échoue explicitement. Migration rejouée → idempotente (aucun doublon). |
| Compatibilité | Archive JSON existante (`docs/migration/matrix.md` §4) étendue au modèle typé avec version d'archive incrémentée ; import des archives antérieures et des exports du prototype (lot 4). PostgreSQL 16+ avec PostGIS (cahier §4). Stockage objet : non couvert (hors dépôt, décision du maître d'ouvrage). |
| Validation | **API** (lot 2) : une commande dont l'écriture du journal échoue (injection de faute en test) ne laisse ni objet ni événement ; `VolumeStore` : écriture, lecture, déduplication par SHA-256, refus au-delà de 25 Mo ; `init.sql` exécuté deux fois sans erreur ni doublon. **CI** : `npm run typecheck` exécute `scripts/check-module-deps.mjs` (aucun import interdit) ; job `e2e` en mode production avec **restauration vérifiée** (`verify-restore.sh` étendu aux tables `atelier_*` et `volumes`, T11). **Lot 4** : archive P.118 exportée puis réimportée → même empreinte du modèle ; archive antérieure importée avec rapport ; **scénario `10-accueil-parametres.mjs`** et `07-documents.mjs` inchangés après bascule. |
| Règles métier | Hypothèses, sources et structure déclarée restent des objets distincts, avec leur statut (R4) ; une donnée absente reste « non évaluée » à l'export comme à l'import (R3). Aucun secret ni clé d'utilisateur dans une archive ou un journal (R18). |
| Extensions à spécifier | Stockage objet des volumes (hors dépôt, §10.1 point 4) ; références externes à la version nommée d'un autre projet (DA-05-11, lot 7) ; politique de récupération des volumes orphelins (durée à fixer par le chef de projet). **Question au maître d'ouvrage** : le stockage des volumes en base (`bytea`) vous convient-il jusqu'à la décision d'hébergement d'un stockage objet ? |
