| Champ | Contenu |

| Identité | DA-21-02 (M16, étape cible P1). Plusieurs clients modifient le même modèle : chaque lot validé crée une révision, chaque client se resynchronise, chaque conflit est détaillé et résolu explicitement. Sous-exigences : -a concurrence optimiste par `baseRevision` ; -b synchronisation incrémentale par le journal ; -c résolution explicite des conflits (409) ; -d rejeu hors ligne. Pas de CRDT sur la géométrie (R17). Référence de comportement : aucune (nouveau comportement Fadi). |
| Situation utilisateur | Éditer en même temps qu'une autre personne, voir ses modifications arriver, et ne jamais perdre ni écraser un lot validé sans le savoir. |
| Entrées et unités | Enveloppe `atelier-commands/1` : `requestId` (UUID, un par lot), `baseRevision` (entier : révision sur laquelle le lot a été préparé), `contract`, `label`, `commands` ; `GET /journal?apres=n` ; `GET /model?revision=n`. Aucune unité propre. |
| Comportement | **Écriture.** `POST /commands` : transaction avec verrou sur la ligne du projet ; `baseRevision` comparée à la révision courante ; égale : application, journal et boîte de sortie dans la même transaction, révision +1, 200 `{ revision, applique, effets, journalId }` ; différente : 409 `{ erreur: "conflit", baseRevision, revisionCourante, conflits: [{ objetId, motif, etatServeur }] }`, où `conflits` liste les objets du lot modifiés ou supprimés depuis `baseRevision` (vide sans recouvrement). Lot atomique : un 400 ou un 409 ne laisse aucune écriture. |
| | **Rebasage.** 409 à `conflits` vide : le client réexécute le lot sur l'état à jour (mêmes réducteurs) puis le renvoie avec `baseRevision` = révision courante ; le serveur le revalide en entier, rien n'est fusionné côté client. Le `requestId` reste celui du lot tant que son contenu est identique, et un `requestId` n'est jamais réutilisé pour un contenu différent. |
| | **Synchronisation.** Après chaque réponse 200, à l'ouverture et à la reprise de connexion, le client lit `GET /journal?apres=n` et applique les entrées dans l'ordre à son état local ; un bandeau « modèle mis à jour : révision n » montre l'écart ; la périodicité de rafraîchissement (ou une poussée) est décidée au lot 2 et consignée dans `decisions.md`. Un objet supprimé par autrui ne réapparaît pas ; un brouillon qui le touche est signalé. |
| | **Conflit.** `conflits` non vide : panneau par `objetId` (motif modifié ou supprimé, état serveur, ma version) ; choix explicites : abandonner mon lot (brouillon conservé) ou le reprendre sur l'état serveur après un nouvel aperçu ; jamais de fusion silencieuse ni de dernier écrit gagnant (R17 : fusion par rejeu validé). |
| Données et dépendances | Révision courante (`projects.model_revision`), journal (`journalId`, `requestId`, révision, auteur, commandes, effets), boîte de sortie, index unique `(project_id, request_id)` ; copie locale Dexie (lecture et file d'envoi, jamais source de vérité) ; aucune classe du modèle propre à la collaboration. |
| Résultats | 200 avec `revision`, `applique`, `effets`, `journalId` ; 409 détaillé avec état serveur ; état local resynchronisé ; lot conservé en brouillon en cas d'abandon. |
| Cas limites | **Concurrence.** Deux lots simultanés sur le même objet : le premier validé l'emporte, le second reçoit 409 avec `conflits[].objetId` ; lot touchant un objet supprimé : 409 (motif « supprimé ») ; niveau supprimé par autrui pendant que j'y ajoute des objets : refus au rejeu ; annulation d'un lot dont un objet a changé depuis : 409 (DA-21-04). **Requête répétée.** Même `requestId` : réponse enregistrée, aucune seconde révision (T06) ; réponse perdue puis renvoi : même résultat. |
| | **Réseau et droits.** Hors ligne : réducteur local, file Dexie (une entrée par lot), rejeu dans l'ordre à la reconnexion, brouillon si incompatible, rien d'abandonné en silence ; rôle `write` exigé (403 motivé), 404 sans accès, 423 pendant une réservation d'autrui (DA-21-01). |
| Compatibilité | Enveloppe `contract: "atelier-commands/1"`, autre valeur refusée (400) ; PostgreSQL (`SELECT … FOR UPDATE` sur la ligne du projet, index unique `(project_id, request_id)`) ; Dexie côté client. |
| | Import P.118 : la copie de travail est un modèle comme un autre, éditée par les mêmes commandes. IFC, DXF : sans objet. |
| Validation | **Unité** (`packages/atelier-model/src/commandes/*.test.ts`) : les réducteurs purs donnent la même sortie (état, inverse, `effets`) côté navigateur et côté serveur pour la même entrée ; un lot rejoué sur un état modifié par autrui produit des conflits détaillés par `objetId`. |
| | **API** (`apps/api/src/routes/atelier-commands.test.ts`, groupe « concurrence ») : deux requêtes à la même `baseRevision` sur le même objet : une 200, une 409 avec `conflits[].objetId` et état serveur, une seule révision ajoutée ; `baseRevision` périmée sans recouvrement : 409 à `conflits` vide, renvoi sur la révision courante : 200 ; même `requestId` : même réponse sans révision ; lot dont une commande est invalide : 400, rien d'écrit ; `GET /journal?apres=n` : entrées dans l'ordre. |
| | **e2e** (`apps/web/e2e/scenarios/05-atelier.mjs`, bloc « Collaboration · édition simultanée ») : deux navigateurs à la même révision sur la copie de travail de P.118 ; A modifie `EX118-mezz-W-009`, B tente de le modifier : conflit affiché avec l'état serveur, choix explicite, aucune perte ; B reçoit la modification de A sans recharger ; coupure réseau simulée : lot en file, rejeu à la reconnexion dans l'ordre ; délai de synchronisation imprimé, sans seuil. |
| Règles métier | Aucune règle réglementaire. R9 : toute modification passe par une commande typée, idempotente, validée par le serveur, journalisée, inversible. R3 : un conflit n'est jamais résolu par une valeur devinée. R10 : bandeau, brouillon et état de synchronisation sont de l'affichage. R11 : après synchronisation, les dérivés concernés sont marqués périmés. R17 : pas de CRDT sur la géométrie ; réservation, variantes et fusion par rejeu validé. Critère B.22 : aucune perte silencieuse de modification validée ; conflits et révisions explicites. |
