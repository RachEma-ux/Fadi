| Champ | Contenu |
| --- | --- |
| Identité | DA-07-17 (M05, étape cible P1). Une zone est un objet de classe `zone` (building.architecture) : contour nommé qui regroupe des pièces et des espaces d'un niveau (relation `contient`). Sous-exigences : -a créer ; -b modifier contour, nom, catégorie et membres ; -c supprimer (famille `zone.*` de l'annexe B). Référence de comportement : prototype, tracés `role = core-zone` de P.118. |
| Situation utilisateur | Regrouper des pièces et des espaces d'un niveau dans un ensemble nommé (par exemple un noyau) pour les lire, les filtrer et, plus tard, les quantifier ensemble. |
| Entrées et unités | `niveauId` ; `polygones` (contour de la zone, `{ x, y, frame: "local", unit: "m" }`) ; `nom` ; `categorie` (texte du projet, aucune liste imposée) ; `contient` (identifiants de pièces et d'espaces du même niveau). Unité autre que m refusée (T03). |
| | Aucun nom, aucune catégorie ni aucun membre par défaut (R3) : absents, ils restent « non évalués ». L'inclusion géométrique d'une pièce ou d'un espace dans le contour est une proposition, jamais une appartenance déduite en silence. |
| Comportement | **Cycle.** Outil « Zone » → contour (tracé ou tracé fermé existant) → paramètres (nom, catégorie) → membres : pièces et espaces dont les polygones sont inclus dans le contour sont proposés (cases à cocher, rien de coché d'office) → aperçu (contour, membres, aire géométrique) → contrôle → validation ; Échap annule sans commande. |
| | **Commandes.** Création (contour, nom, catégorie et membres en un lot), modification (contour, nom, catégorie, ajout ou retrait de membres) et suppression de zone (famille `zone.*`) ; supprimer une zone ne supprime jamais ses membres, listés dans les effets. Appartenance explicite : une pièce ou un espace peut appartenir à plusieurs zones (regroupement, non partition) ; les recouvrements de zones sont signalés, jamais refusés. |
| | **Sans correction silencieuse (R12).** Membre hors du contour, membre déplacé : écart listé avec proposition (retirer, agrandir le contour). Suppression d'une pièce ou d'un espace : l'appartenance est retirée dans le même lot (effets listés, inverse restitué). Palette (UX2) : « zone » ; synonymes « secteur », « noyau » ; exemple court : regrouper deux pièces dans une zone nommée (exemple, jamais valeur par défaut) ; aide (UX4). |
| Données et dépendances | Classe `zone` ; relation `contient` (zone → pièces et espaces) ; `niveauId` ; `piece` et `espace` référencés par `objetId`. `core-geometry` (inclusions, aires) ; événement `atelier.commande.validee` : vues, quantités et bilan Harmonie « à recalculer » (R11, T07) ; microversion +1. |
| Résultats | Zone créée, modifiée ou supprimée ; membres et écarts listés dans le panneau des modifications ; inverse = valeurs et appartenances précédentes. |
| Cas limites | **Valeurs.** Contour non fermé, auto-intersecté ou d'aire sous la tolérance : refusé (400 avec `chemin`) ; membre d'un autre niveau, inexistant ou d'une classe autre que `piece` ou `espace` : refusé ; zone vide (aucun membre) : admise ; zone dans une zone : refusée (extension). |
| | **Concurrence, réseau, droits.** `baseRevision` dépassée et zone ou membre modifié ou supprimé depuis → 409 avec `conflits[].objetId` et état serveur ; même `requestId` → réponse enregistrée, aucune seconde révision (T06) ; hors ligne : réducteur local, file Dexie, rejeu dans l'ordre, brouillon si incompatible ; 403 motivé, 404 sans accès, 423 pendant une réservation d'autrui (R13). |
| Compatibilité | Import P.118 (section 6) : tracés `role = core-zone` → `zone` ; aucune appartenance n'est déduite à l'import (jamais devinée, R3) : `contient` reste vide, l'aperçu propose les pièces incluses ; effectif donné par le rapport d'import. |
| | IFC (annexe C, lot 6) : `IfcZone` et regroupement des `IfcSpace` par la relation de l'annexe C (`IfcRelAggregates`), à valider par le corpus IFC (R16). DXF : aucune sortie propre. |
| Validation | **Unité** (`packages/atelier-model/src/commandes/zone.test.ts`) : création avec membres ; membre d'un autre niveau refusé ; inclusion géométrique proposée, rien coché ; suppression d'une pièce membre : appartenance retirée puis restituée par l'inverse ; suppression de la zone : membres intacts ; pièce dans deux zones : recouvrement signalé ; inverse restitue l'état. |
| | **API** (`apps/api/src/routes/atelier-commands.test.ts`) : création de zone avec membres → 200, révision +1, `effets` ; membre inexistant → 400 avec `chemin` ; même `requestId` → même réponse ; `baseRevision` périmée et zone ou membre modifié → 409 avec `conflits[].objetId` ; rôle lecture → 403 ; réservation d'autrui → 423. |
| | **e2e** (`apps/web/e2e/scenarios/05-atelier.mjs`, bloc « 2D · pièces, espaces, zones ») : copie de travail de P.118 : zones issues de `core-zone` listées comme le rapport d'import, sans membre déduit ; créer une zone avec deux pièces, annuler, rétablir ; second navigateur à la même révision. |
| Règles métier | Aucune règle réglementaire (zonage, secteurs d'incendie, affectations : non fournis ; règles selon pays, usage et version identifiés, à fournir avec leur source). R3 : aucune appartenance déduite en silence. R9 : tout par commande ; R10 : niveau actif et sélection hors révision ; R11. |
| Extensions à spécifier | Zones imbriquées ; zones sur plusieurs niveaux ; propriétés agrégées (aire totale, nombre de pièces) et quantités par zone (lot 5) ; zones issues d'une règle d'affectation (règle à fournir avec sa source). |
