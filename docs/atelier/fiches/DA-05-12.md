| Situation utilisateur | L'architecte sélectionne un objet quelconque et veut savoir ce qu'il est, d'où viennent ses valeurs (saisies, importées, calculées), le modifier dans l'inspecteur avec des unités claires, retrouver ce qui en dépend (ouvertures, cotations, vues) et le retrouver dans le navigateur. Résultat : chaque objet du modèle est identifiable, typé, traçable et modifiable par commande. |
| Entrées et unités | Identifiant (`${projectId}_${id}`, attribué par le réducteur à la création — **hypothèse** : identifiant généré côté client dans la commande pour permettre l'aperçu hors ligne et l'idempotence, à figer par L1.2). Paramètres de la classe (cahier §5.2), chacun `{ value, unit }` (m, m², °) ou coordonnée `{ x, y, frame: "local", unit: "m" }`. Propriété typée : `nom` (texte), `valeur` (nombre, texte, booléen), `unite` (obligatoire pour une grandeur), `provenance` ∈ {`saisie`, `import`, `calcul`, `regle`}, `statut` ∈ {`declaree`, `verifiee`, `a-verifier`}. Aucune valeur par défaut tirée de P.118 (R3). |
| Comportement | Création : par la commande de la classe (annexe B : `mur.tracer`, `ouverture.poser`, `solide.extruder`, `esquisse.*`…). Modification de paramètres : `<classe>.modifier`. Propriété libre : `propriete.definir` (annexe B ; `cibles: objetIds`, `params: { nom, valeur, unite, provenance: "saisie" }`), inverse = `propriete.definir` avec l'ancienne valeur ou retrait. Plusieurs objets sélectionnés : seules les propriétés communes, valeurs différentes affichées « (multiples) ».<br>Navigateur : niveau → classe → objets (nom ou identifiant court), effectifs ; clic = sélection (affichage, R10). |

| Cas limites | Paramètre obligatoire manquant, unité incompatible (`mm` au lieu de `m` si non converti explicitement), valeur non finie → 400 `{ chemin, message }` (T03). Repère autre que `local` pour un objet du bâtiment → 400 (R5). Propriété de grandeur sans unité → 400. Tentative de modifier une valeur dérivée (`aireCalculee`) → refus « valeur calculée ». Tentative de passer une valeur importée au statut `verifiee` sans source → refus (**proposé**). Identifiant déjà utilisé (y compris par un objet supprimé) → 400. Objet modifié par un autre utilisateur depuis `baseRevision` → 409 `{ objetId, motif, etatServeur }`. Deux représentations `parametrique` pour un objet → invariant violé, refus du réducteur (R15). Requête répétée → T06 ; lecteur → 403 ; réservation → 423 ; hors ligne : commandes locales rejouées, incompatibles → brouillon visible. |
| Compatibilité | **Import P.118** : les identifiants source sont uniques par famille (220 murs, 120 poteaux, 84 portes, 126 fenêtres, 32 escaliers, 967 tracés, 64 cotations, 95 textes ; ex. `EX118-ss-W-009`) et sont conservés comme base de l'identité (`${projectId}_${idSource}`, **proposé**) et en propriété `idSource` de provenance `import` ; les 45 `rooms[]` n'ont **pas** d'identifiant : identité déterministe dérivée de `level` + `code` (45 couples uniques, vérifié — **proposé**, à figer par L1.4, condition de l'import idempotent). Champs source non canoniques (`lineRef`, `color`, `designRevision`, `sourceMarker`, `clearWidthVerified`…) → propriétés de provenance `import`, statut `declaree`. Représentation des objets importés : `parametrique` (paramètres présents dans les données, proposition §4.2), jamais `importee` pour P.118. **IFC 4.3** (lot 6) : `GlobalId` dérivé de l'identité de façon stable ; propriétés → `IfcPropertySet` ; un objet importé d'IFC a une représentation `importee` sans historique paramétrique inventé (R16). |
