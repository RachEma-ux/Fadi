| Identité | **DA-21-04** « Version management » (Exigences V4, annexe B.22, module M16, étape cible P1 ; critère commun B.22). Retenue aux lots 2 et 7. Modèle de versions « Git-like » du Concept V4 §8 (microversion, version nommée immuable, branche, fusion assistée, publication non bloquante), ramené à Fadi par la proposition §4.7 et le cahier §5.5. Sous-exigences : **DA-21-04-a** (lot 2) **microversion** : chaque lot de commandes validé produit la révision `n + 1` (`projects.model_revision`), jamais réécrite ; **-b** (lot 2) lire le modèle à une révision passée (`GET /model?revision=n`) ; **-c** (lot 7) **version nommée** : instantané immuable d'une révision (nom, auteur, date, empreinte), consultable et comparable ; **-d** (lot 7) **variante** : fork du journal à partir d'une révision, travail isolé ; **-e** (lot 7) **fusion** par rejeu validé des commandes de la variante sur le tronc, avec la liste des objets affectés, mise en évidence 3D et conflits explicites ; **-f** (lot 7) **publication** figée (révision, versions de catalogues, documents), restaurable avec ses dépendances (T11, T12). Fiches liées : DA-21-06, DA-21-07, DA-21-02, DA-21-08 (comparaison de vues, lot 7, hors de ce lot de fiches). |
| Situation utilisateur | L'architecte travaille ; chaque modification est une microversion qu'il peut relire ; au lot 7, il nomme « APS déposé » la révision 312, essaie une variante d'implantation des sanitaires sans toucher au tronc, la fusionne en voyant ce qui change, et publie un dossier figé pendant que la conception continue. |
| Entrées et unités | Lot 2 : `revision` (entier ≥ 0, ≤ révision courante). Lot 7 : nom de version (texte, unique par projet), révision source ; variante : nom, révision de départ ; fusion : variante, révision cible du tronc ; publication : révision, liste de documents, versions de catalogues (types, ontologie, moteur de géométrie). Pas d'unité physique. |
| Comportement | **Lot 2** : `GET /model?revision=n` reconstruit l'instantané typé à la révision `n` en appliquant, depuis l'état courant, les inverses enregistrés des commandes de révision > `n` (ou par rejeu depuis le début ; choix d'implémentation délégué au chef de projet, §10.2, à consigner), et renvoie l'empreinte de l'instantané ; la réponse indique explicitement `revision` et qu'il ne s'agit pas de l'état courant ; aucune écriture n'est possible sur un instantané passé (lecture seule, R11 pour ce qui en dérive). **Lot 7** : version nommée = enregistrement immuable (`atelier_versions`) pointant une révision et son empreinte ; variante (`atelier_variants`) = journal parallèle partant d'une révision ; fusion = rejeu, commande par commande, sur l'état courant du tronc, chaque commande revalidée par le serveur ; toute commande refusée arrête la fusion et est présentée (objets, motif, état du tronc), jamais résolue automatiquement (D3) ; publication (`atelier_publications`) = révision + versions de catalogues + documents produits à cette révision, figée ; la conception continue sur le tronc. |
| Données et dépendances | `projects.model_revision`, `atelier_commands` (`base_revision`, `result_revision`, `commands`, `inverse`), `atelier_objects.model_revision` ; lot 7 : `atelier_versions`, `atelier_variants`, `atelier_publications` (cahier §5.5) ; `produced_documents` (documents à une révision, existant) ; `VolumeStore` (volumes immuables référencés) ; `scripts/verify-restore.sh` étendu (T11). |
| Résultats | Lot 2 : instantané typé lisible à toute révision passée, avec empreinte. Lot 7 : versions nommées, variantes, rapport de fusion, publications restaurables. |
| Cas limites | `revision` > révision courante ou négative → 400 ; révision antérieure à l'import (0) → modèle vide ou état d'import selon la règle d'import (L1.4), explicite. Instantané passé dont une commande n'a pas d'inverse enregistré → erreur explicite, jamais un instantané approximatif. Lot 7 : nom de version déjà pris → refus ; suppression d'une version nommée → refusée (immuable) ; fusion d'une variante dont la révision de départ a été réécrite → impossible par construction (journal non réécrit) ; publication citant un document périmé → refus (R11). |
| Compatibilité | Remplace l'historique par clé de l'Atelier actuel ; l'archive JSON du projet (lot 4) exporte le modèle typé et son journal selon le manifeste versionné (cahier §5.10, T15). Aucun format externe au lot 2. |
| Validation | **Unité `packages/atelier-model`** : appliquer une suite de commandes puis leurs inverses dans l'ordre inverse rend l'empreinte de chaque révision intermédiaire (propriété testée sur P.118 importé). **API** (lot 2) : après trois commandes, `GET /model?revision=n` pour chaque `n` renvoie l'empreinte attendue ; `revision` invalide → 400 ; rôle `read` → 200. **Scénario `05-atelier.mjs`** : tracer, annuler, rétablir → révisions 1 → 2 → 3 persistées (forme reprise du contrôle actuel « révision 1 → 2 → 3 → 4 ») ; **`08-collaboration.mjs`** : second navigateur à la même révision. Lot 7 : version nommée créée puis relue identique après dix commandes ; variante créée, modifiée, fusionnée avec rapport ; conflit de fusion explicite ; publication restaurée par `verify-restore.sh` avec ses dépendances (T12). |
| Règles métier | Sans objet réglementaire. Une version nommée ou une publication ne vaut pas validation réglementaire ni structurelle (R3) ; elle fige un état. |
