# DA-21-04 — Version management / Gestion des versions — module M16 → Collaboration et Atelier — lot 2

**État : spécifiée (lot 0)** (à spécifier → spécifiée → prototype → vérifiée → disponible). Preuve liée : —.

| Champ | Contenu |
| --- | --- |
| Identité | DA-21-04 (M16, étape cible P1). Au lot 2, une version du modèle est une révision numérotée : chaque lot validé, chaque annulation et chaque rétablissement produit une révision (`projects.model_revision` + 1). Sous-exigences : -a consulter l'état du modèle à une révision (`GET /model?revision=n`) ; -b annuler et rétablir (`POST /commands/annuler`, `/commands/retablir`) ; -c versions nommées, variantes, restauration d'une révision : extension (lot 7). Référence de comportement : aucune (nouveau comportement Fadi). |
| Situation utilisateur | Retrouver l'état du modèle à une révision donnée, annuler une modification validée sans réécrire l'historique, et distinguer la révision courante de celles qui l'ont précédée. |
| Entrées et unités | `revision` (entier ≥ 0, paramètre de `GET /model?revision=n` ; absent : révision courante) ; entrée du journal visée (`journalId`) pour annuler et rétablir ; enveloppe habituelle (`requestId`, `baseRevision`, `label` du lot, affiché dans l'historique). Aucune unité propre. |
| Comportement | **Consulter.** `GET /model?revision=n` renvoie l'instantané typé (niveaux, objets, relations, définitions, calques, site, hypothèses, sources) à cette révision, en lecture seule ; révision inexistante ou future : 404 motivé. Le client affiche « révision n, la courante est m » et n'émet aucune commande depuis une révision antérieure ; consulter une révision n'en crée pas (R10). |
| | **Annuler et rétablir.** `POST /commands/annuler` applique l'inverse enregistré d'une entrée du journal : c'est un nouveau lot, une nouvelle révision (`inverseDe` = entrée annulée), jamais une suppression d'historique ; `POST /commands/retablir` rejoue l'entrée annulée. Si un objet touché par l'entrée a été modifié ou supprimé depuis, 409 avec `conflits[].objetId` : aucune annulation partielle ni forcée. |
| | **Affichage.** Liste des révisions (numéro, libellé du lot, auteur, date) dans le panneau des modifications ; la révision consultée est toujours nommée ; états vide (aucune révision antérieure), chargement et erreur explicites (R20). |
| | **Versions nommées et variantes (lot 7).** Jalon nommé, variante, restauration d'une révision antérieure : extension, hors lot 2. Les numéros de révision du lot 2 en sont la base (une version nommée désignera une révision et son empreinte, R11) et ne sont jamais renumérotés ni réutilisés. |
| Données et dépendances | `projects.model_revision` ; journal (`journalId`, révision, `inverseDe`, `label`, auteur) ; reconstruction de l'état à la révision n par le journal ou par instantanés : choix de stockage du lot 2, consigné dans `decisions.md` ; documents dérivés portant révision et empreinte (R11, DA-21-07). Événement `atelier.commande.validee` après chaque annulation ou rétablissement validé. |
| Résultats | Instantané en lecture seule à la révision demandée ; nouvelle révision pour chaque annulation ou rétablissement validé ; historique complet conservé ; 409 détaillé si l'inverse n'est plus applicable. |
| Cas limites | **Valeurs.** Révision négative ou non entière : 400 avec `chemin` ; inexistante ou future : 404 ; annulation d'une entrée déjà annulée : refusée ; rétablissement sans annulation préalable : refusé ; entrée du journal inconnue : 404. |
| | **Concurrence, réseau, droits.** `baseRevision` périmée : 409 ; annulation d'une entrée dont un objet a été modifié depuis : 409 avec `conflits[].objetId` et état serveur ; même `requestId` → réponse enregistrée, aucune seconde révision (T06) ; hors ligne : annuler et rétablir locaux mis en file avec les lots, rejeu dans l'ordre, brouillon si incompatible ; 403 / 404 / 423 selon R13. |
| Compatibilité | Contrat `atelier-commands/1` ; format de l'instantané = celui de `GET /model` (section 5.4), identique pour toute révision ; import P.118 : même numérotation que tout modèle, sans règle particulière ; tout export (IFC, DXF, lots 5 et 6) porte la révision et l'empreinte dont il est issu (R11). |
| Validation | **Unité** (`packages/atelier-model/src/commandes/*.test.ts`) : pour chaque commande, appliquer puis appliquer l'inverse restitue l'état bit à bit ; rétablir après annuler restitue l'état appliqué ; inverse non applicable (objet modifié depuis) : conflit détaillé. |
| | **API** (`apps/api/src/routes/atelier-commands.test.ts`, groupe « versions ») : `GET /model?revision=n` : instantané identique à l'état de la révision n (empreinte enregistrée) ; révision future : 404 ; `POST /commands/annuler` → 200, révision +1, `inverseDe` renseigné, historique conservé ; annuler une entrée dont l'objet a changé depuis : 409 avec `conflits[].objetId` ; rétablir ; même `requestId` : même réponse ; rôle lecture : 403 sur annuler et rétablir. |
| | **e2e** (`apps/web/e2e/scenarios/05-atelier.mjs`, bloc « Collaboration · révisions ») : copie de travail de P.118 : trois lots validés, une révision antérieure consultée en lecture seule (aucune commande émise depuis elle), annuler puis rétablir : révision +1 chaque fois, état final identique à celui d'avant l'annulation ; second navigateur à la même révision : mêmes entrées. |
| Règles métier | Aucune règle réglementaire. R3 : l'état consulté est celui enregistré à la révision demandée, jamais reconstitué par déduction. R9 : commandes inversibles, journalisées. R10 : consulter une révision ne touche pas la révision courante. R11 : un document porte la révision dont il est issu. Critère B.22 : conflits et révisions explicites, aucune perte silencieuse de modification validée. |
| Extensions à spécifier | Versions nommées (jalons), variantes, restauration d'une révision, publication : lot 7 ; fusion de variantes par rejeu validé (R17) ; comparaison de deux versions (DA-21-08, P2). |
