# DA-21-06 — Change tracking / Suivi des modifications — module M16 → module Fadi Atelier (avec Collaboration) — lot 2 (panneau : lot 3a)

**État : spécifiée** (à spécifier → spécifiée → prototype → vérifiée → disponible). Preuve liée : — (journal et route au lot 2, L2.2 ; panneau des modifications au lot 3a, L3a.1).

| Champ | Contenu |
| --- | --- |
| Identité | **DA-21-06** « Change tracking » (Exigences V4, annexe B.22, module M16, étape cible P1 ; critère commun B.22). Retenue aux lots 2 et 7. Objet : chaque modification validée du modèle est **tracée** (qui, quand, quoi, sur quels objets, depuis quelle révision, avec quel inverse) et lisible par l'utilisateur, par projet et par objet. Sous-exigences : **DA-21-06-a** (lot 2) journal des commandes `atelier_commands` (`request_id`, `contract`, `label`, `base_revision`, `result_revision`, `commands`, `inverse`, `effets`, `author_id`, `created_at`, `inverse_of`) ; **-b** (lot 2) lecture incrémentale `GET /journal?apres=n` ; **-c** (lot 3a) panneau des modifications : liste lisible (libellé, auteur, date, révision, objets touchés), filtre par auteur, niveau, classe ; **-d** (lot 3a) historique d'un objet dans l'inspecteur (commandes qui l'ont créé ou modifié) ; **-e** (lot 2) intégration au « journal des révisions » du module Collaboration (existant), qui liste aujourd'hui les écritures du modèle natif ; **-f** (lot 3a) localiser les objets d'une entrée du journal (sélection et cadrage). Fiches liées : DA-21-07, DA-21-04, DA-17-16, DA-21-02. |
| Situation utilisateur | En rouvrant P.118, l'architecte veut savoir ce qui a changé depuis sa dernière visite : il ouvre le panneau des modifications, voit « Tracer un mur — par X, 3 oct., révision 41 → 42 », clique et arrive sur le mur ; dans l'inspecteur d'une porte, il voit qui l'a déplacée et quand. |
| Entrées et unités | Révision de départ `apres` (entier) ; filtres (auteur, niveau, classe, période) ; identifiant d'objet (historique). Libellé de commande (`label` de l'enveloppe, en français, ex. « Tracer un mur ») ; dates en UTC stockées, affichées dans le fuseau du navigateur. |
| Comportement | Chaque validation écrit une entrée de journal dans la même transaction que le modèle (DA-21-05). Annuler / rétablir écrivent une **nouvelle** entrée avec `inverse_of` (l'historique n'est jamais réécrit, proposition §4.4). Le panneau des modifications lit `GET /journal?apres=n` (paginé), groupe par lot de commandes, affiche libellé, auteur, date, révisions et objets touchés (avec leur nom lisible), et l'état de synchronisation des commandes locales en attente (`local`, `conflit`) au-dessus des entrées validées. Historique d'objet : entrées du journal dont les effets citent l'objet. Un objet supprimé reste listé dans l'historique (avec mention « supprimé à la révision m »). Les entrées produites par l'importeur P.118 apparaissent comme une seule entrée « Import de l'exemple P.118 » avec son rapport (R7). |
| Données et dépendances | `atelier_commands` (journal), `effets` (objets créés / modifiés / supprimés, relations, références), `users` (auteur) ; route `GET /projects/:projectId/atelier/journal` ; module Collaboration (`routes/collaboration.ts`, journal des révisions existant, lu depuis les données datées) ; panneau des modifications et problèmes (`apps/web/src/modules/atelier/ui/**`). |
| Résultats | Journal complet et lisible ; historique par objet ; journal des révisions du module Collaboration à jour. |
| Cas limites | `apres` supérieur à la révision courante → liste vide (pas d'erreur). Journal long → pagination stable par révision. Auteur dont le compte a été supprimé → « compte supprimé », entrée conservée. Commande refusée (400 / 403 / 409 / 423) → **pas** d'entrée au journal serveur ; elle reste visible côté client comme brouillon ou conflit. Lecteur (`read`) → journal lisible. Données sensibles : le journal ne contient que les paramètres de commandes du projet, jamais de secret (R18). |
| Compatibilité | Remplace, pour l'Atelier, les « écritures du modèle natif » listées dans le journal des révisions du module Collaboration ; les autres sources de ce journal (arbitrages Harmonie, générations, transferts, documents produits, commentaires) restent inchangées. |
| Validation | **API** (lot 2) : trois commandes → trois entrées avec auteur, révisions et inverses ; annuler → nouvelle entrée `inverse_of` ; `GET /journal?apres=1` → les entrées des révisions 2 et 3 seulement ; commande refusée → aucune entrée ; rôle `read` → 200. **Scénario `05-atelier.mjs`** (lot 3a) : après « tracer un mur, poser une porte, annuler, rétablir », le panneau des modifications liste quatre entrées dans l'ordre, avec l'auteur ; clic sur une entrée → objet sélectionné ; historique de la porte dans l'inspecteur. **`08-collaboration.mjs`** : une commande de B apparaît chez A avec l'auteur B ; le journal des révisions du module Collaboration la liste. **`11-accessibilite.mjs`** : panneau parcouru au clavier. |
| Règles métier | Sans objet réglementaire. |
| Extensions à spécifier | Motif de changement saisi par l'utilisateur (Architecture V4 §7 « motifs de changement ») ; comparaison de géométrie, propriétés et documents entre deux révisions (DA-21-08, lot 7) ; export du journal (lot 5). |
