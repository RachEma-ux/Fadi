Preuve liée : `apps/api/src/routes/atelier-commands.test.ts` (journal dans la transaction, `GET /journal?apres=n`), panneau des modifications (`atelier-nouveau.mjs`) ; compte rendu `lots/lot-2.md`.

| Champ | Contenu |
| --- | --- |
| Identité | DA-21-06 (M16, étape cible P1). Chaque lot validé est une entrée du journal du modèle : qui, quand, quoi, avec quels effets et quel inverse. Sous-exigences : -a journal écrit dans la transaction du lot ; -b lecture incrémentale (`GET /journal?apres=n`) ; -c panneau des modifications de l'Atelier ; -d historique d'un objet. Référence de comportement : aucune (nouveau comportement Fadi). |
| Situation utilisateur | Savoir qui a modifié quoi et quand, retrouver l'historique d'un objet et vérifier qu'aucune modification validée n'a disparu. |
| Entrées et unités | `apres` (révision, entier ≥ 0) ; contenu minimal d'une entrée : `journalId`, `requestId`, révision, auteur, date, `label`, commandes (type, `cibles`), `objetIds`, `effets`, `inverseDe` ; filtres de lecture côté client (auteur, type de commande, `objetId`, intervalle de révisions : affichage, R10). Aucune unité propre. |
| Comportement | **Écriture.** L'entrée est écrite dans la même transaction que la modification, la boîte de sortie et `model_revision` + 1 (section 5.4) : une entrée existe si et seulement si le lot est validé ; un lot refusé (400, 403, 404, 409, 423) n'écrit rien. Le journal est en ajout seul : aucune entrée n'est modifiée ni supprimée ; annuler ou rétablir ajoute une entrée (`inverseDe`). |
| | **Lecture.** `GET /journal?apres=n` renvoie les entrées de révision supérieure à n, dans l'ordre, par pages ; le client s'en sert pour se resynchroniser (DA-21-02) ; le droit `read` suffit. |
| | **Panneau des modifications.** Liste des entrées (libellé, auteur, date, nombre d'objets) et détail des effets (objets créés, modifiés, supprimés ; problèmes créés ; références à réparer ; dérivés périmés) ; un lot de N commandes est un seul élément (« Déplacer N objets »). Aucune correction depuis le panneau : seules annuler et rétablir (DA-21-04) agissent, par commandes (R9). |
| | **Historique d'un objet.** Filtre par `objetId` : modifications dans l'ordre des révisions, auteur et date ; un objet supprimé garde son historique, marqué « supprimé » ; une scission relie l'objet d'origine aux nouveaux objets dans les effets. |
| Données et dépendances | Journal (`journalId`, révision, `requestId`, auteur, horodatage, `label`, commandes, `objetIds`, `effets`, `inverseDe`) ; objets référencés par `objetId` stable ; aucune classe du modèle modifiée ; événement `atelier.commande.validee`. |
| Résultats | Entrées lisibles par révision ; historique par objet ; effets détaillés ; trace de chaque annulation et de chaque rétablissement. |
| Cas limites | **Intégrité.** Lot de N commandes : une entrée, N effets ; deux lots simultanés : ordre de révision fixé par la transaction, jamais d'entrée en double ; même `requestId` : aucune seconde entrée (T06) ; 409 : aucune entrée. **Lecture.** `apres` supérieur à la révision courante : liste vide ; négatif ou non entier : 400 avec `chemin`. |
| | **Réseau et droits.** Hors ligne : entrées locales (lots en file, état « local » puis « synchronisé ») ; 403 / 404 selon R13 ; le journal d'un projet sans accès n'est pas lisible (404). |
| Compatibilité | Journal en JSON typé, contrat `atelier-commands/1`. Import P.118 et IFC : aucun historique antérieur n'est inventé (R3, R16) ; le journal ne contient que les lots validés depuis la création du modèle. Export de l'historique (CSV, PDF) : non couvert ; DXF : sans objet. |
| Validation | **Unité** : chaque réducteur renvoie ses `effets` (créés, modifiés, supprimés, problèmes) ; ils sont reportés tels quels dans l'entrée (égalité entre les `effets` du réducteur et ceux de l'entrée écrite). |
| | **API** (`apps/api/src/routes/atelier-commands.test.ts`, groupe « journal ») : lot valide → une entrée, `journalId` renvoyé, révision +1 ; lot refusé (400, 403, 409, 423) → aucune entrée ; annuler → entrée avec `inverseDe` ; `GET /journal?apres=n` : entrées supérieures à n, dans l'ordre ; `apres` hors bornes : liste vide ou 400 ; même `requestId` : aucune seconde entrée. |
| | **e2e** (`apps/web/e2e/scenarios/05-atelier.mjs`, bloc « Collaboration · suivi ») : copie de travail de P.118 : trois modifications par deux navigateurs, panneau des modifications identique des deux côtés ; historique du mur `EX118-mezz-W-009` dans l'ordre ; annuler : nouvelle entrée, ancienne entrée toujours lisible. |
| Règles métier | Aucune règle réglementaire. R9 : toute modification journalisée et inversible. R12 : références à réparer visibles dans les effets. R10 : filtres et panneau sont de l'affichage. R11 : les dérivés périmés par une entrée sont listés dans ses effets. Critère B.22 : aucune perte silencieuse de modification validée. |
| Extensions à spécifier | Export de l'historique ; commentaires attachés à une entrée ; notifications ciblées (auteur d'un objet modifié) ; rétention et archivage du journal ; comparaison graphique de deux révisions (DA-21-08, P2). |
