# DA-05-14 — Standard-part libraries / Catalogue de types versionné (définitions) — module M04 → module Fadi Atelier — lot 1 + 3a

**État : spécifiée** (à spécifier → spécifiée → prototype → vérifiée → disponible). Preuve liée : — (à lier aux lots 1 et 3a).

Interprétation (proposition `docs/atelier-drawall.md` §5.1) : « bibliothèques de types (14 / 15 = catalogue de
portes / fenêtres / murs versionné) ». Répartition retenue par cette fiche (**recommandation**, ambiguïté
signalée) : **DA-05-14** = le catalogue lui-même — définitions de types, leur version, leur édition ;
**DA-05-15** = l'usage du catalogue — choisir un type, placer ou changer le type d'une occurrence, mettre à jour
la version de catalogue d'un projet. Lot 1 : définitions, commandes, import P.118, versions (L1.1, L1.2, L1.4) ;
lot 3a : panneau du catalogue (L3a.3 « catalogue de types »).

| Situation utilisateur | L'architecte veut des types de murs (et, s'il le décide, de portes et fenêtres) nommés et partagés dans le projet : « Cloison », « Mur », plus ceux qu'il définit ; en modifiant un type, il voit quelles occurrences changent ; il sait quelle version du catalogue a servi à une publication. Résultat : un catalogue de types versionné, sans valeur inventée. |
| Entrées et unités | Définition : `classe` (`mur`, `porte`, `fenetre`, `ouverture`), `identifiant` (texte stable, ex. `cloison`), `nom` (texte), `categorie` (texte libre, ex. « cloison »), `classeIfc` (ex. `IfcWallType`, annexe C), `proprietes` typées facultatives `{ nom, valeur, unite, provenance, statut }`. **Recommandation** : au lot 3, un type ne porte **pas** de dimension imposée (épaisseur, largeur, hauteur restent sur l'occurrence) — P.118 montre des épaisseurs hétérogènes dans un même type (`cloison` : 0,08 / 0,12 / 0,15 / 0,20 m ; `mur` : 0,04 / 0,05 / 0,08 / 0,16 / 0,20 m). Une dimension de type facultative, si l'utilisateur la saisit, sert de **valeur proposée** à la création, jamais d'écrasement des occurrences existantes. Composition, matériaux, résistance au feu, isolation : **non évaluées** (aucune saisie au lot 3). Version de catalogue : entier croissant par projet. |
| Comportement | Commandes de l'annexe B : `type.definir` (`params: { classe, identifiant, nom, categorie, classeIfc, proprietes? }`) → nouvelle définition, version de catalogue + 1 ; inverse : retrait de la définition (refusé si une occurrence l'utilise — **proposé**). `type.modifier` (`cibles: [definitionId]`, paramètres modifiés) → version + 1 ; inverse : `type.modifier` avec les anciennes valeurs. Suppression d'un type : `type.supprimer` (**nom proposé, à figer par L1.2**, absent de l'annexe B), refusée si des occurrences l'utilisent sans type de remplacement dans le même lot.<br>Cycle UX3 : panneau « Catalogue de types » (navigateur du projet) → inspecteur du type → **aperçu** (liste et effectif des occurrences qui l'utilisent, vues marquées) → contrôle → validation.<br>Versionnement (T15) : `atelier_definitions` conserve chaque version (`definition_id`, `version`, contenu) ; une occurrence référence la définition ; une publication (lot 7) fige la version de catalogue utilisée. |
| Données et dépendances | `atelier_definitions` (cahier §5.5 ; contenu par proposition §4.2 : « type de mur (composition, épaisseur, matériau), type de porte / fenêtre (dimensions, sens) … ; version du catalogue d'origine ») ; `atelier_objects.definition_id`. Modules : `atelier-model` (ontologie : classes admettant un type ; réducteurs ; validation), API, interface (panneau catalogue), Documents (nomenclatures par type, lot 5, marquées « à recalculer »), échanges (lot 6 : `IfcWallType`, `IfcDoorType`, `IfcWindowType`). Événement `atelier.commande.validee` pour toute modification de type utilisé. |
| Résultats | Définitions créées / modifiées ; version de catalogue incrémentée ; occurrences touchées listées ; vues et nomenclatures marquées « à recalculer » si une propriété affichée change ; journal, révision `n + 1`. |
| Cas limites | Identifiant de type en double dans la classe → 400. Classe sans type admis (ex. `esquisse.ligne`) → 400. Propriété de grandeur sans unité → 400 (T03). Type `non-type` : réservé (créé par l'import et pour les objets sans type), non supprimable, non renommable (**proposé**). Projet ouvert avec une version de catalogue plus récente que celle connue du client hors ligne → commande rejouée sur la version serveur ; si incompatible → brouillon visible. Requête répétée → T06 ; lecteur → 403 ; 423. |
| Compatibilité | **Import P.118** (cahier §5.2, §6) : `walls[].type` ∈ {`cloison` 135, `mur` 61, absent 24} → définitions `cloison`, `mur`, `non-type` (classe `mur`), version de catalogue 1, provenance `import` ; aucune dimension mise sur ces types (hétérogènes). **Portes et fenêtres** : la source ne porte aucun type ; `openingType` des portes (`sliding` 38, `hinged` 1, `sectional` 1, absent 44) et `mark` sont des propriétés de l'occurrence, conservées en provenance `import`. Les 126 fenêtres ont toutes 2,40 × 2,10 m, allège 0,80 m : **aucun type n'est déduit** de cette régularité (pas de création silencieuse — R3, R7) ; **recommandation** : définition `non-type` pour les ouvertures importées, création de types laissée à l'utilisateur. **IFC 4.3** (lot 6, annexe C) : `IfcWallType` (+ `IfcDoorType`, `IfcWindowType`, hors annexe C, à décider), `IfcRelDefinesByType`. Catalogue Fadi existant `packages/domain-model/src/building-library.ts` : bibliothèque de **programmes** de bâtiments, sans rapport avec ce catalogue de types (pas de confusion). |
