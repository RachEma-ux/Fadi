# DA-05-14 — Standard-part libraries / Bibliothèques de pièces standard (types de murs et formes) — module M04 → Atelier — lot 3a

**État : prototype (lot 3a)** (à spécifier → spécifiée → prototype → vérifiée → disponible). Preuve liée : recette `apps/web/e2e/atelier-nouveau.mjs`, tests `apps/web/src/modules/atelier/nouveau/nouveau.test.ts` et `packages/atelier-model/src/commandes/commandes.test.ts` ; compte rendu `lots/lot-3a.md`.

| Champ | Contenu |
| --- | --- |
| Identité | DA-05-14 (M04, étape cible P1). Interprétation retenue : en architecture, les « pièces standard » sont des types constructifs réutilisables d'un catalogue versionné (`definition`, §5.2) : ici les types de murs (`typeId` : `cloison`, `mur`, `non-type`) et les formes de poteaux (`formeId`) ; à ne pas confondre avec `piece`, la pièce d'un bâtiment. Sous-exigences : -a définir un type (`type.definir`) ; -b modifier un type, version n + 1 (`type.modifier`) ; -c consulter le catalogue et ses usages ; -d appliquer un type à un mur. Les types de portes, de fenêtres et d'ouvertures suivent la même mécanique (DA-05-15). |
| Situation utilisateur | Définir une fois les types de murs du projet, les appliquer, les faire évoluer sans casser les murs existants et savoir où chaque type est employé. |
| Entrées et unités | `type.definir` : `classe` (`mur`), `typeId` (identifiant stable, unique), `nom`, `valeurs` facultatives (`epaisseur`, `hauteur` : `{ value, unit: "m" }` ; `alignement`), propriétés facultatives (DA-06-07). `type.modifier` : `typeId`, `modifications`, `propager` (liste explicite d'identifiants de murs, vide par défaut). Application : `typeId` dans `mur.tracer` ou `mur.modifier`. |
| Comportement | **Cycle.** Panneau Types (catalogue, version, nombre de murs) → type existant ou « Nouveau type » → paramètres → aperçu (murs qui emploient le type, écarts) → contrôle → validation ; Échap annule sans commande. Un type propose des valeurs à la création d'un mur et sert de repère d'écart ; il n'impose rien à un mur existant. |
| | **Version et propagation.** `type.modifier` crée la version n + 1 ; chaque mur garde ses propres `epaisseur` et `hauteur` (valeurs canoniques de l'occurrence, R15) et la version du type sur laquelle il a été aligné. L'aperçu liste les murs qui s'écartent du type ; « propager » ne modifie que les murs cochés, dans le même lot, effets listés : jamais de réécriture silencieuse (R3, R12). |
| | **Contrôles.** `typeId` en double refusé ; valeur sans unité ou unité ≠ m refusée (T03) ; épaisseur ≤ 0 refusée ; classe autre que `mur` refusée au lot 3a (`poteau`, `solide` : extension) ; mur rattaché à un type inconnu refusé ; propagation à un mur d'un calque verrouillé : lot refusé en entier ; aucune suppression de type à l'annexe B (extension). |
| | **Palette (UX2) et aide (UX4).** « type de mur », « types » ; synonymes « catalogue », « type » ; exemple court : définir un type nommé « Type A » et l'appliquer à 3 murs (jamais une valeur par défaut). |
| Données et dépendances | Entité `definition` (classe `mur`, `typeId`, `nom`, `version`, `valeurs`, provenance `import` ou `saisie`, propriétés, classification) ; `typeId` et version d'alignement portés par chaque `mur` (§5.2) ; relation d'usage dérivée. Formes de poteau : `formeId` conservé tel quel (`basic-square`), non modifiable au lot 3a, aucune forme ni aucun profilé normalisé ajouté (aucune donnée structurelle inventée, R3). Événement de commande validée : vues et quantités « à recalculer » (R11, T07) ; microversion +1. |
| Résultats | Type créé ou nouvelle version ; murs alignés à la demande, listés ; catalogue versionné consultable avec ses usages ; inverse = version précédente et valeurs précédentes des murs propagés. |
| Cas limites | **Valeurs.** Type sans valeur : valide (valeurs « non évaluées ») ; modification qui ne change rien : refusée (aucune version vide) ; mur importé de type `non-type` ou sans type : conservé tel quel, jamais « corrigé » vers `mur` ou `cloison` ; propagation dont l'épaisseur ferait sortir une ouverture de son hôte : ouverture « à réparer » avec propositions (R12). |
| | **Concurrence et réseau.** `baseRevision` dépassée et type modifié depuis → 409 avec `conflits[].objetId` (le `typeId`) et état serveur ; mur supprimé par autrui pendant une propagation : 409, il ne réapparaît pas ; même `requestId` → une seule version (T06). Hors ligne : réducteur local, file Dexie, rejeu dans l'ordre, brouillon si la version du type a changé. 403 / 404 / 423 selon R13. |
| Compatibilité | Import P.118 : types de murs `cloison`, `mur`, `non-type` importés tels quels en `definition` (nom conservé, provenance `import`, valeurs seulement si l'export en déclare, sans les compléter) ; 220 murs gardent leur `typeId` ; 120 poteaux de forme `basic-square`. IFC : `IfcWallType` avec `IfcRelDefinesByType` à l'export (annexe C, lot 6) ; types importés d'IFC : définitions de provenance `import`. DXF : sans objet. |
| Validation | **Unité** (`packages/atelier-model/src/commandes/type.test.ts`) : `type.definir` ; doublon refusé ; `type.modifier` : version + 1, murs inchangés sans `propager` ; avec `propager` : seuls les murs cités changent, effets listés ; unité ≠ m refusée ; mur de type inconnu refusé ; types importés conservés à l'identique ; inverse restitue type et murs. |
| | **API** (`apps/api/src/routes/atelier-commands.test.ts`) : `type.definir` puis `type.modifier` → 200 et `effets` ; `typeId` en double → 400 avec `chemin` ; même `requestId` → même version ; `baseRevision` périmée et type modifié → 409 ; rôle lecture → 403. |
| | **e2e** (`apps/web/e2e/scenarios/05-atelier.mjs`, bloc « Organisation · types de murs ») : copie de travail de P.118 : le catalogue liste `cloison`, `mur`, `non-type` avec leur nombre de murs et la forme `basic-square` (120 poteaux) ; définir un type, tracer un mur de ce type, modifier le type avec et sans propagation ; annuler ; second navigateur à la même révision. |
| Règles métier | Aucune règle réglementaire : épaisseurs minimales, compositions, résistances ne sont ni fournies ni présumées (R3) ; les valeurs d'un type sont des valeurs déclarées. R9 : toute création ou évolution d'un type passe par une commande. |
| Extensions à spécifier | Composition d'un mur en couches et matériaux ; retrait ou suppression d'un type ; types de poteaux et formes de profil ; catalogues partagés entre projets (lot 7) ; bibliothèques normalisées ou de fabricants (DA-05-17, DA-05-18 : P2). |
