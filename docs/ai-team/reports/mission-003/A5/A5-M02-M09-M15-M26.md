### 1. Périmètre et modèle de menace

Risque confirmé : `apps/api/vitest.setup.ts` charge `.env.test` sans override ; `apps/api/src/db/client.ts` construit un Pool à partir de DATABASE_URL ;12fichiers `.test.ts` exécutent TRUNCATE CASCADE. Les47scénarios navigateur effectuent aussi des mutations HTTP et ont des BASE_URL par défaut. `scripts/verify-restore.sh`, le démarrage image qui applique un schéma et les opérations d’import/génération doivent figurer dans la carte des lanceurs ; la garde Vitest seule ne les sécurise pas.

La protection couvre erreur de configuration, héritage d’environnement, cible inconnue, confusion pool/endpoint et réexécution après reconnexion. Un utilisateur malveillant capable de modifier code et descripteur n’est pas contenu par un booléen ou un type TypeScript ; l’isolement réseau et les permissions DB restent nécessaires. Aucun test ne doit contacter une production pour prouver son refus.

### 3. Algorithme obligatoire et effets autorisés

0. Construire un environnement enfant minimal sans credential production, sans variables libpq implicites ; pas de bootstrap `.env` général dans le lanceur test. Capturer la configuration une fois, sans modifier globalement process.env du serveur productif.

4. Comparer tuple canonique à l’attestation et à la politique des endpoints de ce run. La politique exclut production/staging/inconnu ; un nom ressemblant à une base test sur un endpoint inconnu reste interdit. Pour un réseau non local, l’authentification serveur et l’isolement font partie du contrat ; pas de simple résolution DNS suivie d’une confiance aveugle.
5. Créer le connecteur seulement après autorisation. Avec timeout et mode lecture seule, lire current_database/current_user, identité serveur attendue, marqueur unique du provisioning, version PostGIS si requise et privilèges du rôle. Le rôle DOIT être dédié, sans superuser/CREATEDB/CREATEROLE/bypassRLS ni accès métier externe. Le marqueur n’est jamais créé pour « faire passer » une attestation ratée.
6. Comparer toutes les identités ; sur erreur fermer la connexion et refuser sans mutation. Les instructions de vérification sont une liste fermée de SELECT ; pas de DDL/reset/migration avant verdict.
7. Seule la session attestée permet reset. Prendre une connexion dédiée ; lier vérification et opération à la même connexion/run ; empêcher concurrence entre suites sur même DB.
